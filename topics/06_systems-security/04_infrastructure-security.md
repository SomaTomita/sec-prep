## ファイアウォール

NIST SP 800-41 Rev.1 が整理する主要な方式:

| 方式 | 判断基準 | 長所/短所 |
|---|---|---|
| パケットフィルタ | 送信元/宛先IP・ポート番号（ヘッダのみ） | 高速だが状態を見ないため単純な偽装に弱い |
| ステートフルインスペクション | コネクションの状態（TCPのSYN/ACK等）を追跡 | 「確立済み通信への応答」を正しく通せる。現在の主流 |
| アプリケーション層（プロキシ） | HTTP等のペイロード内容まで検査 | 精度は高いが処理が重く、対応プロトコルが必要 |
| NGFW（次世代ファイアウォール） | 上記に加えアプリ識別・侵入防御を統合 | 実質的にIDS/IPSと機能統合している製品が多い |

### ルール例（デフォルト拒否、[01](./01_security-fundamentals.md)のフェイルセーフ原則の実装）

```
許可: 送信元 any    宛先 10.0.0.5:443  (HTTPS のみ通す)
許可: 送信元 10.0.0.0/24  宛先 10.0.0.5:22  (社内からのSSHのみ)
拒否: それ以外すべて  ← 明示的に許可していない通信はすべて落とす
```

## IDS/IPS（侵入検知/防御システム）

NIST SP 800-94 の分類:

```
IDS（Intrusion Detection System）: 不審な通信を検知してアラートを出す（通信は止めない）
IPS（Intrusion Prevention System）: 検知に加えて、その場で通信を遮断する
```

検知方式は2種類:

| 方式 | 仕組み | 弱点 |
|---|---|---|
| シグネチャベース | 既知の攻撃パターン（バイト列・正規表現）と照合 | 未知の攻撃（ゼロデイ）を検知できない |
| 異常検知ベース | 平常時のトラフィックからの統計的逸脱を検出 | 誤検知（false positive）が多くなりがち |

Martin Roeschが1999年に発表した **Snort** はシグネチャベースの代表的なOSS NIDS
（Network IDS）で、軽量さを売りに当時の商用製品の代替として設計された。
シグネチャの例（Snortルール文法の概念的な形）:

```
alert tcp any any -> 10.0.0.5 80 (content:"' OR '1'='1"; msg:"Possible SQLi";)
```

`content` に典型的なSQLインジェクション文字列を置くことで、既知パターンの通信を検知する
——[02](./02_software-vulnerabilities.md) のInjection攻撃を、アプリ側の対策と別の層
（ネットワーク層）で検知する多層防御の一例。

## ネットワークセグメンテーションとゼロトラスト

### 伝統的な境界防御モデル

```mermaid
flowchart LR
    NET["インターネット"] --> FW1["ファイア<br>ウォール"]
    FW1 --> DMZ["DMZ<br>（公開サーバ群）"]
    DMZ --> FW2["ファイア<br>ウォール"]
    FW2 --> LAN["社内LAN"]
```

DMZ（非武装地帯）に外部公開サーバを置き、内部LANとの間にもう1段ファイアウォールを挟む
ことで、公開サーバが侵害されても内部LANへの直接到達を防ぐ（VLAN＝スイッチ上でネットワークを
論理的に分割する技術、による分割も同じ目的）。
この設計の前提は「境界の内側は信頼できる」という考え方。

### ゼロトラストアーキテクチャ（NIST SP 800-207, 2020年）

```
原則: 「社内ネットワークにいるから信頼する」という暗黙の信頼を排除する
実装: すべてのアクセス要求を、発信元のネットワーク位置に関わらず
      その都度アイデンティティ・デバイスの状態・文脈で検証してから許可する
```

リモートワーク・BYOD（私物端末の業務利用）・クラウド利用の拡大で「社内ネットワークの内側」という境界自体が
曖昧になったことが背景。[03](./03_authn-authz-access-control.md)のABAC（属性ベースアクセス制御）
は、ゼロトラストを実装する際の認可判定エンジンとして自然に組み合わさる
——「毎回の要求を、その時の属性で判定する」という発想が共通しているため。

## なぜ重要か / コースでの位置づけ

「インフラストラクチャに組み込まれたセキュリティ技術」がこの章の内容。
ファイアウォール/IDS/IPSは[02](./02_software-vulnerabilities.md)のアプリ層の脆弱性が
突かれた後の**検知・遮断**を担い、[03](./03_authn-authz-access-control.md)の認可モデルは
ゼロトラストの中核として実装される。「アプリを完璧に直す」ことと「ネットワークで
多層に守る」ことは互いを代替しない、両輪の関係にある。

## 演習（解答つき）

1. ステートフルインスペクション型ファイアウォールが、単純なパケットフィルタ型より
   優れている点を一言で述べよ。
2. シグネチャベースIDSが未知の攻撃を検知できない理由を述べよ。
3. ゼロトラストアーキテクチャが「社内LANにいるから安全」という前提を排除する理由を、
   リモートワーク普及と絡めて説明せよ。

<details><summary>解答</summary>

1. パケットフィルタは各パケットを独立に見てヘッダだけで判定するが、ステートフル
   インスペクションはコネクションの状態（SYN送信済みか等）を追跡できるため、
   「確立済み通信への正当な応答」と「なりすましの新規パケット」を区別できる。
2. シグネチャベースは既知の攻撃パターンとの照合でしか検知できないため、
   一致するシグネチャが存在しない新種・未公開（ゼロデイ）の攻撃はすり抜けてしまう。
3. リモートワークやBYOD、クラウド利用の拡大により、正規の利用者・デバイスが
   もはや「社内ネットワークの内側」だけからアクセスするとは限らなくなった。
   ネットワーク位置と信頼性の相関が崩れたため、位置に頼らず毎回アイデンティティや
   デバイスの状態を検証する方式に移行する必要が生じた。

</details>
