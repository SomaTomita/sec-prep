# 01. Secure SDLC と SecDevOps

> 対応科目: Security Through the Software Lifecycle ｜ 次: [02 脅威モデリング](./02_threat-modeling.md) ｜ 層: 基礎(Layer 1)

**この1ページで分かること**

- セキュリティを開発ライフサイクル全体に埋め込む理由（shift-left）と、NIST SSDF の4つの実践グループ
- 運用フェーズの1ステップの不備が全体を崩した実例（Equifax, 2017年）
- CI/CD パイプラインに SAST・SCA・DAST を組み込む DevSecOps の形

## 一言で

家を建て終わってから耐震補強するより、図面の段階で入れる方が安い——ソフトウェアも同じで、セキュリティを要件定義から運用・廃棄までの**ライフサイクル全体**に埋め込む（shift-left＝検証を工程の左＝早い段階へ寄せる）。

### 最小の例: ログイン機能 1 つ

| 工程 | 普通にやること | 足すセキュリティ活動 1 つ |
|---|---|---|
| 要件 | 「ID とパスワードで入れる」 | 「5 回失敗で一時ロック」を要件に書く |
| 実装 | 比較コードを書く | 静的解析ツールでハードコードされた鍵を検出 |
| テスト | 正しい ID で入れるか | 間違った ID を 1 万回投げて落ちないか |
| 運用 | 動かす | 使っているライブラリの脆弱性情報を監視 |

各工程に 1 つずつ足すだけで、ライフサイクル全体に埋め込んだ形になる。以下、その一般論。

## 押さえる概念

### セキュリティ問題が成立する3つの条件

次の 3 つが揃って初めてセキュリティ問題になる。

| 条件 | 内容 |
|---|---|
| **資産** | 守る価値のあるもの |
| **利害の異なるステークホルダ** | 同じ資産に対して保護要求が食い違う主体が複数いること |
| **敵対者** | それを狙う主体がいること |

**どれかが欠けると別の問題になる。**

```
敵対者がいない        → 信頼性・安全性の問題（故障や事故への対処）
利害の対立がない      → 単なる要件定義（守り方は一意に決まる）
守る資産がない        → そもそも問題ではない
```

2 番目が厄介。EC サイトの購買履歴は利用者には秘匿したいもの、事業者には活用したい資産。**この対立は技術では解けず、設計者が優先順位を決める**しかない。

> 「資産・脅威・脆弱性・リスク・対策」という**語彙とリスク計算**は
> [`../06_systems-security/01_security-fundamentals.md`](../06_systems-security/01_security-fundamentals.md) が本体。
> 本ファイルが足すのは「セキュリティ問題が成立する条件」という別の切り口。

### 対策と攻撃は共進化する

3 番目の条件（敵対者）が他の品質特性と決定的に違う点。**敵対者は戦略的**——こちらの対策を見てから次の手を選ぶ。

```
良い対策を入れる
  → 敵はその対策を迂回する「次に安い攻撃」へ移る
  → 完全に安全な系は存在しない
```

よって「一度作って終わり」にならず、**継続的な活動として組み込む**必要がある。攻撃側の自動化で共進化の速度も上がる（→ [AI とセキュリティ](../00_overview/05_ai-and-security.md)）。

### NIST SSDF（SP 800-218）の4つの実践グループ

Microsoft SDL（2002 年）を業界横断に一般化した米国政府標準。「いつ何をするか」でなく「何を達成すべきか」を定義する。

| 実践グループ | 内容 | 具体例 |
|---|---|---|
| PO (Prepare the Organization) | 組織・人・ツールの準備 | セキュリティ教育、コーディング規約の整備 |
| PS (Protect the Software) | ソフトウェア自体の完全性を守る | ソースコード管理のアクセス制御、ビルドの署名 |
| PW (Produce Well-Secured Software) | 設計・実装・テストで欠陥を作り込まない | 脅威モデリング（[02](./02_threat-modeling.md)）、SAST/ファジング（[04](./04_security-testing.md)）、SBOM（ソフトウェア部品表＝依存ライブラリとバージョンの一覧） |
| RV (Respond to Vulnerabilities) | 出荷後に見つかった脆弱性への対応 | 脆弱性開示窓口、パッチ配布、根本原因分析 |

### なぜ「ライフサイクル全体」が要るのか——Equifaxの事例（2017年）

RV を怠ると PO/PS/PW がどれだけ良くても崩れる実例。

```
2017-03-07: Apache Struts の脆弱性 CVE-2017-5638 が公開され、パッチも同時公開
2017-03-09: Equifax社内でパッチ適用の指示が出るが、担当者が実施しなかった
2017-03-15: 脆弱性スキャンを実施するが、この脆弱性を検出できなかった
2017-05〜07: 攻撃者が同じ脆弱性を悪用してデータベースに侵入、情報を持ち出す
2017-07-29: 「不審な通信」を検知して初めてパッチを適用（攻撃開始から2ヶ月以上後）
結果: 米国消費者1億4300万人分の氏名・社会保障番号・生年月日等が流出
```

**設計・実装（PW）が正しくても、運用（RV）の 1 ステップが止まれば既知・パッチ済みの穴が 2 か月放置される**。Secure SDLC が「廃棄まで」を範囲に含む理由。

### SecDevOps（DevSecOps）：CI/CDパイプラインへの組み込み

```mermaid
flowchart LR
    C["コミット"] --> B["ビルド"] --> S1["SAST: コードを実行せず解析"] --> S2["SCA: 依存ライブラリを既知脆弱性と照合"]
    S2 --> T["テスト"] --> S3["DAST: 動作中アプリへ疑似攻撃"] --> D["デプロイ"] --> M["ランタイム監視"]
```

各段にゲート（重大な脆弱性が出たらパイプラインを止める）を置き、「最後に専門チームがレビュー」から「書いた瞬間にフィードバック」へ変える。これが DevSecOps の核心。手法の中身は [04](./04_security-testing.md)。

## 演習（解答つき）

1. Equifaxの事例で、崩れたのはSSDFのどの実践グループ（PO/PS/PW/RV）か、理由も述べよ。
2. 「セキュリティは最後にペネトレーションテストで確認すればよい」という考え方が
   shift-left の発想と対立する理由を一言で述べよ。
3. CI/CDパイプラインにSASTとSCAの両方を組み込む意味を、それぞれが検出する対象の違いから述べよ。

<details><summary>解答</summary>

1. **RV（Respond to Vulnerabilities）**。脆弱性自体は3月7日に公開・パッチ済みだったため
   PW（設計・実装段階の欠陥作り込み防止）の問題ではなく、パッチ適用というRVのプロセスが
   機能しなかったことが2ヶ月以上の侵入を許した直接原因。
2. shift-left は「欠陥は発見が遅いほど修正コストが指数関数的に増える」という前提に立ち、
   要件・設計段階から検証を始める。ペネトレーションテストは開発の最終盤に行うため、
   見つかった欠陥の修正コストが最も高い段階でしか検出できない。
3. SASTはソースコード自体の欠陥（バッファオーバーフローになりうる書き方等、自社で書いた
   コードの問題）を検出するのに対し、SCAは依存する外部ライブラリに**既知の**CVEが
   含まれていないかを検出する。Equifaxの事例はまさに後者（外部ライブラリの既知脆弱性）
   の管理が漏れたケースで、SCA/SBOMがあれば影響範囲の特定が迅速化できた。

</details>
