# 01. タイミング攻撃と定数時間実装

> 親: [README](./README.md) ｜ 次: [02 電力解析](./02_power-analysis.md) ｜ 層: 基礎(Layer 1)

最も理解しやすいサイドチャネルは**実行時間**である。測定機器も物理的な接触も不要で、
処理にかかった時間を測るだけで成立する。まず4桁の PIN 検証を実際に破ってみて、
「なぜ総当たりより桁違いに速いのか」を手で確認する。

---

## 脆弱な実装

PIN を1桁ずつ比較し、不一致が見つかった時点で即座に戻る——ごく自然な書き方である。

```
verify(input[4], secret[4]):
    for i in 0..3:
        if input[i] != secret[i]:
            return FALSE      ← ここで即座に戻る
    return TRUE
```

**問題**: 正解している桁が多いほど、ループが長く回る。
つまり**実行時間が「先頭から何桁一致したか」を漏らしている**。

```
入力 0000 で secret=7391 を検証 → 1桁目で不一致 → ループ1回で終了（速い）
入力 7000 で secret=7391 を検証 → 2桁目で不一致 → ループ2回で終了（少し遅い）
```

---

## 手で破る

1桁目を 0〜9 まで試し、**最も実行時間が長かった候補**を採用する。それが正解の桁である。
確定したら2桁目に進み、同じことを繰り返す。

```
1桁目: 0〜9 を試す → 7 のとき最も遅い → 1桁目 = 7 と確定
2桁目: 70〜79 を試す → 73 のとき最も遅い → 2桁目 = 3 と確定
3桁目: 730〜739 を試す → …
4桁目: 7390〜7399 を試す → …
```

### 計算量の比較

```
総当たり:         10 × 10 × 10 × 10 = 10⁴ = 10,000 通り
タイミング攻撃:   10 + 10 + 10 + 10 = 10 × 4 = 40 通り（上限）
```

**指数から線形に落ちる**——これが本質である。桁数 `n` に対して `10ⁿ` が `10n` になる。
PIN を6桁に延ばしても、総当たりは100万通りになるが、タイミング攻撃では60通りにしかならない。

**桁数を増やすという対策がほとんど効かない。** 秘密の長さで守るという発想が、
情報が1桁ずつ漏れる状況では成立しなくなる。

> **実務上の注意**: 実際には測定にノイズが乗るため、各候補を複数回測って平均を取る。
> それでも試行回数は桁数に比例したままで、指数には戻らない。
> ネットワーク越しでも、十分な回数を測れば成立しうる。

---

## 対策：定数時間実装

```
原則: 秘密データの値によって「実行時間・アクセスするメモリアドレス・分岐の方向」が
      変わってはいけない
```

上の PIN 検証なら、**早期 return をやめて必ず全桁を比較する**。

```
verify_ct(input[4], secret[4]):
    diff = 0
    for i in 0..3:
        diff = diff | (input[i] XOR secret[i])   ← 差分を累積するだけ
    return (diff == 0)                            ← 最後に一度だけ判定
```

一致・不一致にかかわらず必ず4回ループするので、実行時間が秘密に依存しなくなる。

### 気をつける3点

| 避けるもの | なぜ危険か |
|---|---|
| **秘密依存の分岐** | `if (secret_bit) {...} else {...}` は分岐予測と実行時間の差として漏れる。分岐なしの算術で書く |
| **秘密依存のテーブル参照** | `table[secret_byte]` は**どのキャッシュラインを読んだか**で秘密の一部を漏らす（→ [03](./03_cache-side-channels.md)） |
| **秘密依存の反復回数** | ループ回数が秘密で変わると、そのまま時間差になる |

### 暗号ライブラリでの実例

通常のユークリッド互除法は入力によって反復回数と分岐が変わる。
これを秘密値（RSA の鍵生成・ECDSA の逆元計算等）に使うと、タイミングから情報が漏れる。

対策は**入力に関わらず常に同じ回数・同じ分岐パターンで動く**アルゴリズムへの置き換えで、
二進 GCD（Stein のアルゴリズム）や Bernstein–Yang の safegcd がそれにあたる。
背景は
[`../../01_prerequisites/01_math-for-crypto/01_modular-arithmetic/04_gcd-euclidean.md`](../../01_prerequisites/01_math-for-crypto/01_modular-arithmetic/04_gcd-euclidean.md) を参照。

> ⚠️ **定数時間で書けば安全、とは言えない。** 投機的実行を悪用すると、
> 定数時間のコードでも漏洩を作れることが 2018年以降に判明している
> （[`../02_hardware-attacks.md`](../02_hardware-attacks.md) の Spectre）。
> 定数時間実装は**必要条件であって十分条件ではない**。

## 演習（解答つき）

1. 4桁 PIN のタイミング攻撃で試行回数が `10⁴` ではなく `10×4` になる理由を一言で述べよ。
   また PIN を8桁に延ばした場合の試行回数の上限を求めよ。
2. 早期 return を削除して全桁を比較するようにした。これだけで定数時間になるか。
   ならない場合、他に何を確認すべきか。
3. `table[secret_byte]` のようなテーブル参照が、実行時間を一定にしても危険なのはなぜか。

<details><summary>解答</summary>

1. **各桁を独立に決定できるため**。実行時間が「先頭から何桁一致したか」を教えるので、
   1桁目を確定してから2桁目に進む、という逐次的な絞り込みが可能になる。
   全体を1つの塊として当てる必要がないので、桁ごとの試行を足し算すればよい。
   8桁なら `10 × 8 = 80` 通り（総当たりは `10⁸ = 1億` 通り）。
2. **ならない。** ループ回数は一定になるが、他に次を確認する必要がある。
   ①ループ内に秘密依存の分岐が残っていないか
   ②秘密依存のメモリアクセス（テーブル参照）がないか
   ③コンパイラが最適化で早期終了を復活させていないか
   （`diff` を使わずに済むと判断して分岐を再導入することがある）。
   ③は実際に起こるため、定数時間性を意図するコードには専用の記述方法が必要になる。
3. 実行される**命令の数と時間**が同じでも、**どのメモリアドレスに触れたか**が
   キャッシュの状態として残る。攻撃者はキャッシュのヒット/ミスの時間差を測ることで
   「どのキャッシュラインが読まれたか」を知り、そこから `secret_byte` の上位ビットを
   推定できる。時間を一定にするだけでは不十分で、**アクセス先も秘密に依存させない**必要がある。

</details>
