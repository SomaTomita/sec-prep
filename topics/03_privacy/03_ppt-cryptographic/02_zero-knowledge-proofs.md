# 02. ゼロ知識証明

> 親: [README](./README.md) ｜ 前: [01 PIR と OT](./01_pir-and-ot.md) ｜ 次: [03 MPC と FHE](./03_mpc-and-fhe.md) ｜ 層: 基礎(Layer 1)

「秘密を明かさずに、自分がその秘密を知っていることを相手に納得させる」——語義矛盾に
見えるが実現できる。Goldwasser–Micali–Rackoff (1985) が定式化した。

**この1ページで分かること**

- ゼロ知識証明の3性質が「それぞれ誰を守るか」
- 健全性に2段階あり、認証に使うなら強い方（knowledge soundness）が必要なこと
- Σプロトコルの3ステップが**なぜ3つ必要か**、任意の計算には制約への変換が要ること

---

## 3つの性質

| 性質 | 主張 | **誰を守るか** |
|---|---|---|
| **完全性** (completeness) | 主張が真で証明者が正直なら、検証者は必ず受理する | **正直な証明者**（正しいのに拒否されない） |
| **健全性** (soundness) | 主張が偽なら、検証者は（高い確率で）拒否する | **検証者**（嘘を通されない） |
| **ゼロ知識性** (zero-knowledge) | 検証者は「主張が真である」以外に何も学べない | **証明者の秘密** |

**3つが別々の主体を守っている**点が重要——どれか1つを外すと誰かが損をする
（ゼロ知識性がなければ、証明のたびに秘密が漏れる）。

---

## 健全性の2段階

「主張が偽なら拒否される」だけでは足りない場面がある。

```
通常の健全性:
  「その主張は真である」ことは保証する
  → しかし証明者が本当に秘密を知っているかは保証しない

knowledge soundness（special soundness とも）:
  「証明者は実際にその秘密を知っている」ことまで保証する
```

**なぜ区別が必要か**: 認証では「私は秘密鍵を知っている」と証明させたいのに、
通常の健全性では「秘密鍵が**存在する**」ことしか保証されない。
**秘密鍵は誰かが持っていれば存在するので、それでは本人確認にならない。**
したがって認証用途では knowledge soundness が必要になる
（*proof of knowledge* と呼ばれる系統。認証プロトコルの一般論は
[`../../02_cryptography/05_protocols/README.md`](../../02_cryptography/05_protocols/README.md)）。

---

## Σプロトコル：3ステップの構造

最も基本的な形が **Σプロトコル**（Schnorr, 1989 が代表例）。
離散対数を知っていることを、その値を明かさずに証明する。

```
証明者                                     検証者
  │  ① commitment（コミットメント）
  │────────────────────────────────────────>│  乱数から作った値を先に固定する
  │                                          │
  │  ② challenge（チャレンジ）               │
  │<────────────────────────────────────────│  検証者がランダムな値を送る
  │                                          │
  │  ③ response（レスポンス）                │
  │────────────────────────────────────────>│  秘密と①②から計算した応答
  │                                          │  → ①②③の整合性を検証する
```

### なぜ3ステップ必要なのか

**この問いに答えられれば、Σプロトコルは理解できている。**

| もし省くと | 何が壊れるか |
|---|---|
| **① commitment を省く** | 証明者がチャレンジを見てから都合のよい値を後付けできる。**健全性が崩れる** |
| **② challenge をランダムにしない** | 証明者が事前に答えを用意できる。**健全性が崩れる** |
| **③ response を返さない** | そもそも何も証明されない |

つまり **①で逃げ道を封じ、②で予測を封じ、③で知識を示す**——
3つが揃って初めて「後出しでも事前準備でもない」ことが保証される。
チャレンジレスポンス認証と同じ構造であり、②が予測できると成立しない点も共通する。

## Fiat–Shamir 変換：対話を消す

Σプロトコルは対話が必要だが、それでは署名のように「一方的に送る」用途に使えない。

```
Fiat–Shamir 変換:
  検証者が選ぶはずのチャレンジを、ハッシュ関数で自分で作る
      challenge = H(commitment ‖ メッセージ)
  → 対話が不要になる（非対話型になる）
```

**証明者が自分でチャレンジを作れるなら健全性が崩れないのか**——崩れないのは、
ハッシュ関数の出力を証明者が制御できないからである。ただしこの議論には
**ランダムオラクル仮定**（ハッシュが完全にランダムな関数として振る舞う）が必要になる。

### 署名方式との繋がり

**この変換の産物が Schnorr 署名であり、その系統に EdDSA がある。**
「秘密鍵を知っていることのゼロ知識証明」に**メッセージをチャレンジに含める**と、
そのメッセージに対する署名になる。つまり
**デジタル署名はゼロ知識証明の応用として理解できる**——
本ファイルで最も見通しのよい接続である。署名方式の詳細は
[`../../02_cryptography/03_public-key-crypto/04_digital-signatures.md`](../../02_cryptography/03_public-key-crypto/04_digital-signatures.md) が本体。

## 任意の計算を証明する：算術回路と R1CS

Σプロトコルが扱えるのは「離散対数を知っている」のような**特定の代数的主張**だけである。
「このプログラムを正しく実行した」のような一般の計算を証明するには変換が必要になる。

```
証明したい計算 → 算術回路（加算と乗算のゲート）
              → R1CS (Rank-1 Constraint System)
              → 証明系にかける → ゼロ知識証明
```

**R1CS は「変数の間に成り立つべき双線形な制約の集合」**として計算を表現したもので、
「この変数の組は正しい計算過程を表している」という主張に置き換えられる。

### この変換が実務の主要コスト

単純な算術は制約が少なく証明も速いが、**ハッシュ関数・比較・分岐を多く含む処理では
制約数が爆発**し、証明生成が重くなる。つまり**プログラムの書き方が性能を決める**——
通常のプログラミングでは軽い処理が算術回路では高コストになる。
ゼロ知識証明の実装が難しいのは暗号の部分ではなく、**この変換を効率よく行う部分**である。

### 証明系の種類

| 系統 | 証明サイズ | 検証時間 | 信頼できるセットアップ |
|---|---|---|---|
| zk-SNARK | 小さい | 速い | **必要な方式が多い** |
| zk-STARK | 大きめ | 速い | 不要 |

**信頼できるセットアップ**（trusted setup）とは、方式の初期化時に生成される秘密のパラメータを
「誰も保持していない」ことを前提にする仕組み。**これが漏れると偽の証明が作れる**ため、
運用上のリスクとして扱われる。不要な方式が好まれる理由がここにある。

## プライバシー応用：選択的開示

```
やりたいこと: 「私は18歳以上である」ことだけを証明し、生年月日は明かさない
```

証明書に生年月日が入っていても、**その値を開示せずに「18歳以上」という述語だけを証明する**。
これが選択的開示であり、匿名credential の基礎になる。
EU デジタルIDウォレットでの議論は
[`../../06_systems-security/07_pki-and-identity.md`](../../06_systems-security/07_pki-and-identity.md)——
**技術的には可能だが制度がそれを要求するとは限らない**という論点に繋がる。
他の主要な応用は暗号通貨のスケーリングと機密取引
（[`../../06_systems-security/05_distributed-systems-security.md`](../../06_systems-security/05_distributed-systems-security.md)）。

## 演習（解答つき）

1. Σプロトコルの3ステップのうち、① commitment を省くと何が壊れるか。
2. 認証用途で「通常の健全性」では不十分な理由を述べよ。
3. 「年齢が18歳以上」だけを証明する方式が、生年月日を開示する方式より優れている理由を
   [`../01_privacy-concepts.md`](../01_privacy-concepts.md) の語彙を使って述べよ。

<details><summary>解答</summary>

1. **健全性が崩れる。** commitment は「チャレンジを見る前に証明者が値を固定した」ことを
   保証している。これがないと、証明者は検証者からチャレンジを受け取ってから
   都合のよい値を逆算して作れてしまう。つまり秘密を知らなくても検証を通せるようになる。
2. 通常の健全性は「主張が真である」ことしか保証しない。認証で証明したい主張は
   「秘密鍵を知っている」だが、**秘密鍵は誰かが持っていれば存在する**ので、
   「存在する」ことの証明では本人確認にならない。
   **証明者自身が知っている**ことまで保証する knowledge soundness が必要になる。
3. 生年月日を開示すると、それが**識別子として機能しうる**——他の情報と組み合わせることで
   個人の特定に使え、複数のサービスでの行動を**連結**する手がかりにもなる。
   「18歳以上」という述語だけなら、その条件を満たす人全体が匿名性集合になり、
   非連結性も保たれる。データ最小化の原則を技術的に実現した形と言える。

</details>
