# 02. パイプラインとハザード（ISA・5段パイプライン・Spectre/Meltdown）

> 親: [README](./README.md) ｜ 前: [01 HDL の役割と設計フロー](./01_hdl-basics.md) ｜ 次: [03 メモリ階層とHW/SW協調設計](./03_memory-hierarchy-and-codesign.md) ｜ 層: 基礎(Layer 1)

洗濯機→乾燥機→たたむ、を 3 人で同時に回せば 3 倍の洗濯物が片付く。CPU も命令を段に分けて同時に流す（パイプライン）。
ただし「前の人の結果待ち」が起きるのがハザードで、その回避策の副作用が Spectre/Meltdown になる。

**この1ページで分かること**

- CPU の5段パイプライン（IF/ID/EX/MEM/WB）が、なぜ毎サイクル1命令ずつ完了できるか
- 命令の依存が生むハザード（データ／制御）と、その回避策（フォワーディング＝結果を配線で先送り、分岐予測）
- 分岐予測に伴う投機実行が Spectre/Meltdown の足がかりになる理由

---

## 最小の例: 3 命令を 3 段で流す

```
          1    2    3    4    5
I1 (ADD)  取出  解読  実行
I2 (SUB)       取出  解読  実行
I3 (LW)             取出  解読  実行
```

サイクル 3 では I1 が実行・I2 が解読・I3 が取出を**同時に**進める。1 命令は 3 サイクルかかるのに、定常状態では毎サイクル 1 命令完了する。

## 命令セットアーキテクチャ（ISA）概観

ISA = CPU が受け付ける命令の「約束事」（命令形式・レジスタ・メモリモデル）。x86-64（PC）、ARM（スマホ）、RISC-V（オープン）。
実習は 8/16 bit マイコン（AVR 等）への C 実装から始まり ISA を意識する場面が出る。

## 5段パイプライン（IF/ID/EX/MEM/WB）

```mermaid
flowchart LR
    IF["IF Fetch"] --> ID["ID Decode"] --> EX["EX Execute"] --> MEM["MEM Memory"] --> WB["WB Write Back"]
```

| 略 | ステージ名 | 役割 |
|---|---|---|
| IF | Instruction Fetch | メモリから命令を取ってくる |
| ID | Instruction Decode | 命令を解読しレジスタを読む |
| EX | Execute | ALU 演算（加算・比較・アドレス計算） |
| MEM | Memory Access | ロード/ストアでデータメモリにアクセス |
| WB | Write Back | 結果をレジスタファイルに書き戻す |

各段は専用回路（組合せ回路＋段間レジスタ）を持ち、別々の命令を同時に処理する。

### パイプライン実行トレース（4命令・8サイクル）

```
          1    2    3    4    5    6    7    8
I1 (ADD)  IF   ID   EX   MEM  WB
I2 (SUB)       IF   ID   EX   MEM  WB
I3 (LW)             IF   ID   EX   MEM  WB
I4 (BEQ)                 IF   ID   EX   MEM  WB
```

`I1: ADD R1,R2,R3` → `I2: SUB R4,R1,R5` → `I3: LW R6,0(R4)` → `I4: BEQ R6,R0,L1`。
レイテンシ（1 命令の所要時間）は 5 サイクルのまま、スループット（単位時間の処理数）だけが上がる。

---

## データハザード

I2 は I1 の結果 `R1` を使うが、I1 が書き戻す WB はサイクル 5、I2 が読む ID はサイクル 3。そのままでは古い値を読む。

| 対策 | 内容 | 限界 |
|---|---|---|
| フォワーディング | I1 の EX 出力を配線で直接 I2 の EX へ渡す。ストール（待ち）なし | ロード命令の結果は MEM 終了まで確定しない |
| ストール | 1 サイクル待つ | ロード直後に同じレジスタを使うと必須（ロード-ユース・ハザード） |

## 制御ハザード

分岐 `BEQ` の成否は EX まで分からないが、IF はその間も次の命令を先読みしている。外れたら取り込んだ命令を**フラッシュ**（捨てる）。
対策が**分岐予測**（履歴から成否を予測）。当たれば待ちなし、外れればフラッシュして取り直す。

## Spectre/Meltdown への接続

投機実行（当たるつもりで先に実行）は、外れてフラッシュされても**キャッシュに触った痕跡は消えない**。
Spectre は禁止領域を投機的に読ませ、その値に依存する番地をキャッシュ時間で観測して値を復元する
（キャッシュは [03](./03_memory-hierarchy-and-codesign.md)、攻撃手順は [`../../../04_hardware-security/02_hardware-attacks.md`](../../../04_hardware-security/02_hardware-attacks.md)）。

## 演習（解答つき）

1. 上のトレース表で、サイクル 5 に IF・ID・EX・MEM・WB のどのステージにどの命令がいるか答えよ。
2. フォワーディングがあってもストールが必要になるハザードの例を1つ挙げ、理由を述べよ。
3. 分岐予測ミスがなぜ Spectre のようなサイドチャネル攻撃の足がかりになるのか、一文で説明せよ。

<details><summary>解答</summary>

1. I1: WB、I2: MEM、I3: EX、I4: ID。
2. ロード-ユース・ハザード（load-use hazard）。ロード命令の結果は MEM ステージが終わるまで
   確定しないため、直後の命令がそれを EX で使おうとしても間に合わず、フォワーディングだけでは
   救えず 1 サイクルのストールが必要になる。
3. 投機実行された命令はアーキテクチャ上の結果（レジスタ・メモリ）は破棄されても、
   実行中にアクセスしたキャッシュの状態は残るため、その残留状態をタイミング測定で読み取れば
   本来見えないはずのデータが間接的に漏れるから。

</details>
