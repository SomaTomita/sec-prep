# C言語とメモリ

> 対応科目: Development of Secure Software / Security Through the Software Lifecycle ｜ 次: [02 プロセスと OS](./02_process-and-os.md) ｜ 層: 基礎(Layer 1)

## 一言で

C言語はメモリを直接操作する。その「直接性」がパフォーマンスを生むと同時に、
プログラマのミスが即メモリ破壊につながる。C系脆弱性の大半はここに根ざす。

**この1ページで分かること**

- ポインタと配列は同じもの（`a[i]` = `*(a+i)`）で、境界チェックが一切ないこと
- プロセスのメモリがどの領域（スタック＝関数呼び出しの一時領域／ヒープ＝手動確保領域）に分かれ、どちら向きに伸びるか
- バッファオーバーフローがなぜリターンアドレス上書きにつながるか

## 押さえる概念

### ポインタと配列

- ポインタはメモリアドレスを格納する変数。`int *p = &x;` で `p` は `x` のアドレスを持つ
- 配列名は先頭要素へのポインタとして扱われる: `a[i]` は `*(a + i)` と等価
- **境界チェックが存在しない**: `a[10]` を宣言して `a[11]` に書いてもコンパイルエラーにならない

#### 具体例: 配列添字とポインタ演算は同じ結果になる

```c
int a[5] = {10, 20, 30, 40, 50};
int *p = a;                 // 配列名 a は先頭要素へのポインタに「減衰」する

printf("%d\n", a[2]);       // 30
printf("%d\n", *(p + 2));   // 30 -- a[i] と *(p+i) は同じ結果
printf("%d\n", *(a + 2));   // 30 -- 添字はポインタ演算の糖衣構文
```

実行結果はどの行も `30`。境界チェックがないので `p + 2` が配列の外を指しても
コンパイル・実行時エラーにはならず、そのまま読み書きされてしまう。

```c
char buf[8];
buf[8] = 'X';  // 未定義動作 — バッファの外を書き換える
```

### メモリレイアウト（典型的なプロセス空間）

図は上ほどアドレスが高く、下ほど低い（一般的な描き方に合わせる）。

```
高アドレス
┌───────────────────────────┐
│ カーネル空間                 │
├───────────────────────────┤
│ スタック                     │ ← 関数呼び出しごとに下（低アドレス側）へ伸びる
│   ↓（使うほど下へ）           │
│   ...空き領域...             │
│   ↑（使うほど上へ）           │
│ ヒープ                       │ ← malloc/free で確保。上（高アドレス側）へ伸びる
├───────────────────────────┤
│ BSS（未初期化静的変数）        │
├───────────────────────────┤
│ データ（初期化済み静的変数）     │
├───────────────────────────┤
│ テキスト（コード）             │ 実行可能、通常読み取り専用
└───────────────────────────┘
低アドレス
```

ヒープとスタックは互いに向き合う形で伸びる設計になっており、両者がぶつかると
メモリ枯渇（ヒープ確保失敗・スタックオーバーフロー）が起きる。

### スタックとヒープの違い

| 項目 | スタック | ヒープ |
|---|---|---|
| 確保 | 自動（関数呼び出し時） | 手動（`malloc`/`free`） |
| 解放 | 自動（関数リターン時） | 手動（解放忘れ→メモリリーク） |
| 速度 | 高速 | 低速（OS要求を含む場合あり） |
| 主な脆弱性 | スタックバッファオーバーフロー | ヒープオーバーフロー、UAF |

### スタックフレームの中身（x86-64 の典型例）

関数呼び出し時にスタックに積まれる要素を、アドレスが高い順に並べると:

```
高アドレス
┌───────────────────────────┐
│ 呼び出し元の引数（7個目以降）  │
├───────────────────────────┤
│ リターンアドレス              │ ← call 命令が自動で push
├───────────────────────────┤
│ 保存された旧 rbp             │ ← push rbp（現在の rbp はここを指す）
├───────────────────────────┤
│ ローカル変数 buf[] など       │ ← rbp-8, rbp-16 … に配置
│      ↑ 書き込みはこちら方向    │
└───────────────────────────┘
低アドレス（rsp 側）
```

スタック自体は高→低アドレス方向に伸びるが、配列への書き込みは低→高方向に進む。
そのため `buf[]` がオーバーフローすると図の**上方向**（保存 rbp → リターンアドレス）を上書きする。
リターンアドレスを書き換えれば、関数リターン時に攻撃者の指定したアドレスへジャンプさせられる
— これがスタックバッファオーバーフロー攻撃の核心。攻撃手法・防御の詳細は
[`06_systems-security/02_software-vulnerabilities.md`](../../06_systems-security/02_software-vulnerabilities.md) で扱う。

### 未定義動作（Undefined Behavior）

C/C++ 標準では「特定の状況での動作は未定義」とされており、コンパイラは最適化で  
そのパスを削除することがある。代表例:

- 配列の範囲外アクセス
- NULL ポインタの参照外し（dereference）
- 初期化前変数の読み取り
- 符号付き整数オーバーフロー
- メモリ解放後のアクセス（Use-After-Free: UAF）

未定義動作は「たまたま動く」ことがあるため発見が遅れ、セキュリティホールになりやすい。

### 危険な標準ライブラリ関数

| 危険な関数 | 理由 | 安全な代替 |
|---|---|---|
| `gets()` | 長さチェックなし | `fgets()` |
| `strcpy()` | コピー先サイズ確認なし | `strlcpy()` / `snprintf(buf, sizeof(buf), "%s", src)`（`strncpy` は null 終端を保証せず非推奨）|
| `sprintf()` | 書き込みサイズ未制限 | `snprintf()` |
| `scanf("%s")` | 長さ制限なし | `scanf("%255s")` など |

## なぜ重要か / コースでの位置づけ

「C系低レベルソフトの脅威」（§6.7）の前提が、まさにここ。  
具体的には:

- **スタックバッファオーバーフロー**: リターンアドレス上書き → シェルコード実行
- **ヒープオーバーフロー**: ヒープメタデータ破壊 → 任意アドレス書き込み
- **フォーマット文字列攻撃**: `printf(user_input)` → 任意読み書き
- **UAF**: 解放済みメモリの再利用 → 型混同による権限昇格

これらすべての攻撃を理解・防御するには「どのメモリ領域に何が配置されるか」の
イメージが不可欠。`02_process-and-os.md` で OS レベルの保護機構（ASLR/NX/カナリア）
と接続する。

## 演習（解答つき）

1. `int a[4] = {1, 2, 3, 4}; int *p = a;` のとき `*(p + 3)` は何を表すか。`a[3]` と同じ値になる理由も述べよ。
2. メモリレイアウトで、ヒープとスタックはそれぞれどちら向きに伸びるか。両者がぶつかると何が起きるか。
3. `buf[8]` が確保されたスタックフレームで、書き込みが `rbp-8` を超えて溢れた場合、最初に破壊される可能性が高いデータは何か。理由も述べよ。

<details><summary>解答</summary>

1. `*(p + 3)` は配列4番目の要素、つまり値 `4`。`a[i]` は `*(a + i)` の糖衣構文であり、
   配列名 `a` は式中でポインタに減衰するため `p` と `a` は同じ演算になる。
2. ヒープは低アドレス→高アドレス（図では上方向）、スタックは高アドレス→低アドレス（図では下方向）に伸びる。
   互いに向き合う形で確保されるため、両者がぶつかるとヒープ確保失敗やスタックオーバーフローが起きる。
3. 保存された旧 `rbp`。書き込みは低アドレス→高アドレス方向に進むため、`buf[]` の直後（高アドレス側）に
   隣接する保存 `rbp` がまず壊れ、さらに溢れるとリターンアドレスにも到達する。

</details>
