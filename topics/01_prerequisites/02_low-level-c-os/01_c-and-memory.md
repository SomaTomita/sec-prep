# C言語とメモリ

> 対応科目: Development of Secure Software / Security Through the Software Lifecycle ｜ 次: [02 プロセスと OS](./02_process-and-os.md) ｜ 層: 基礎(Layer 1)

## 一言で

メモリは「番地つきの巨大なロッカー列」、C 言語はその番地を直接指定して読み書きする言語。
速い代わりに、番地を 1 つ間違えても誰も止めてくれない。C 系脆弱性の大半はここに根ざす。

**この1ページで分かること**

- ポインタと配列は同じもの（`a[i]` = `*(a+i)`）で、境界チェックが一切ないこと
- プロセスのメモリがどの領域（スタック＝関数呼び出しの一時領域／ヒープ＝手動確保領域）に分かれ、どちら向きに伸びるか
- バッファオーバーフローがなぜリターンアドレス上書きにつながるか

## 押さえる概念

### 最小の例: 変数 1 個とその番地

```c
int x = 42;      // 値 42 を入れた箱
int *p = &x;     // p には x の番地（例: 0x7ffd...c8）が入る
printf("%d", *p); // 番地の中身を読む → 42
```

`x` が箱、`&x` が箱の番地、`*p` が「番地の中身」。C の全操作はこの 3 つの組み合わせ。

### ポインタと配列

| 用語 | 意味 |
|---|---|
| ポインタ | メモリアドレス（番地）を入れる変数。`int *p = &x;` で `p` は `x` の番地を持つ |
| 配列名 | 先頭要素へのポインタとして扱われる。`a[i]` は `*(a + i)` と同じ |
| 境界チェックなし | `a[10]` を宣言して `a[11]` に書いてもエラーにならない |

```c
int a[5] = {10, 20, 30, 40, 50};
printf("%d %d", a[2], *(a + 2));  // 30 30 — 添字はポインタ演算の糖衣構文
char buf[8]; buf[8] = 'X';        // 未定義動作 — 外を書いても止まらない
```

### メモリレイアウト（典型的なプロセス空間）


```
高アドレス
┌───────────────────────────┐
│ カーネル空間                 │
├───────────────────────────┤
│ スタック                     │ ← 関数呼び出しごとに下（低アドレス側）へ伸びる
│   ↓（使うほど下へ）           │
│   ...空き領域...             │
│   ↑（使うほど上へ）           │
│ ヒープ                       │ ← malloc/free で確保。上（高アドレス側）へ伸びる
├───────────────────────────┤
│ BSS（未初期化静的変数）        │
├───────────────────────────┤
│ データ（初期化済み静的変数）     │
├───────────────────────────┤
│ テキスト（コード）             │ 実行可能、通常読み取り専用
└───────────────────────────┘
低アドレス
```

ヒープ（`malloc` で手動確保する領域）とスタック（関数呼び出しごとに自動で使う領域）は向き合って伸び、
ぶつかるとメモリ枯渇（ヒープ確保失敗・スタックオーバーフロー）になる。

### スタックとヒープの違い

| 項目 | スタック | ヒープ |
|---|---|---|
| 確保 | 自動（関数呼び出し時） | 手動（`malloc`/`free`） |
| 解放 | 自動（関数リターン時） | 手動（解放忘れ→メモリリーク） |
| 速度 | 高速 | 低速（OS要求を含む場合あり） |
| 主な脆弱性 | スタックバッファオーバーフロー | ヒープオーバーフロー、UAF |

### スタックフレームの中身（x86-64 の典型例）

関数呼び出し時にスタックに積まれる要素を、アドレスが高い順に並べると:

```
高アドレス
┌───────────────────────────┐
│ 呼び出し元の引数（7個目以降）  │
├───────────────────────────┤
│ リターンアドレス              │ ← call 命令が自動で push
├───────────────────────────┤
│ 保存された旧 rbp             │ ← push rbp（現在の rbp はここを指す）
├───────────────────────────┤
│ ローカル変数 buf[] など       │ ← rbp-8, rbp-16 … に配置
│      ↑ 書き込みはこちら方向    │
└───────────────────────────┘
低アドレス（rsp 側）
```

スタックは高→低へ伸びるが、配列への書き込みは低→高へ進む。だから `buf[]` が溢れると図の**上**
（保存 rbp → リターンアドレス＝関数が終わったら戻る番地）を上書きする。戻る番地を書き換えれば、
関数終了時に攻撃者の指定した場所へジャンプする。これがスタックバッファオーバーフロー攻撃の核心
（攻撃・防御の詳細は [`06_systems-security/02_software-vulnerabilities.md`](../../06_systems-security/02_software-vulnerabilities.md)）。

### 未定義動作（Undefined Behavior）

標準が「この場合の動作は決めない」と宣言している状況。コンパイラは最適化でそのパスを丸ごと消すこともある。

| 代表例 | 一言 |
|---|---|
| 配列の範囲外アクセス | 境界チェックがないため気づけない |
| NULL ポインタの参照外し（dereference） | 何もない番地を読む |
| 初期化前変数の読み取り | ゴミ値が出る |
| 符号付き整数オーバーフロー | 上限を超えた瞬間の値が未定義 |
| 解放後のアクセス（Use-After-Free: UAF） | 返却済みメモリを使い続ける |

「たまたま動く」ことがあるため発見が遅れ、セキュリティホールになりやすい。

### 危険な標準ライブラリ関数

| 危険な関数 | 理由 | 安全な代替 |
|---|---|---|
| `gets()` | 長さチェックなし | `fgets()` |
| `strcpy()` | コピー先サイズ確認なし | `strlcpy()` / `snprintf(buf, sizeof(buf), "%s", src)`（`strncpy` は null 終端を保証せず非推奨）|
| `sprintf()` | 書き込みサイズ未制限 | `snprintf()` |
| `scanf("%s")` | 長さ制限なし | `scanf("%255s")` など |

## なぜ重要か / コースでの位置づけ

「C系低レベルソフトの脅威」（§6.7）の前提がここ。

| 攻撃 | 何が起きるか |
|---|---|
| スタックバッファオーバーフロー | リターンアドレス上書き → シェルコード実行 |
| ヒープオーバーフロー | ヒープ管理情報の破壊 → 任意アドレス書き込み |
| フォーマット文字列攻撃 | `printf(user_input)` → 任意読み書き |
| UAF | 解放済みメモリの再利用 → 型混同による権限昇格 |

どれも「どの領域に何が置かれるか」のイメージが前提。OS 側の防御（ASLR/NX/カナリア）は次ファイル。

## 演習（解答つき）

1. `int a[4] = {1, 2, 3, 4}; int *p = a;` のとき `*(p + 3)` は何を表すか。`a[3]` と同じ値になる理由も述べよ。
2. メモリレイアウトで、ヒープとスタックはそれぞれどちら向きに伸びるか。両者がぶつかると何が起きるか。
3. `buf[8]` が確保されたスタックフレームで、書き込みが `rbp-8` を超えて溢れた場合、最初に破壊される可能性が高いデータは何か。理由も述べよ。

<details><summary>解答</summary>

1. `*(p + 3)` は配列4番目の要素、つまり値 `4`。`a[i]` は `*(a + i)` の糖衣構文であり、
   配列名 `a` は式中でポインタに減衰するため `p` と `a` は同じ演算になる。
2. ヒープは低アドレス→高アドレス（図では上方向）、スタックは高アドレス→低アドレス（図では下方向）に伸びる。
   互いに向き合う形で確保されるため、両者がぶつかるとヒープ確保失敗やスタックオーバーフローが起きる。
3. 保存された旧 `rbp`。書き込みは低アドレス→高アドレス方向に進むため、`buf[]` の直後（高アドレス側）に
   隣接する保存 `rbp` がまず壊れ、さらに溢れるとリターンアドレスにも到達する。

</details>
