# 01. エンティティ認証

> 親: [README](./README.md) ｜ 次: [02 鍵管理](./02_key-management.md) ｜ 層: 基礎(Layer 1)

[`../04_hash-and-mac.md`](../04_hash-and-mac.md) の MAC や署名は
「**このデータは改ざんされていない**」ことを保証した。本ファイルが扱うのは別の問題——
「**この相手は今そこにいる本人か**」である。似ているが、必要な性質が違う。

**この1ページで分かること**

- データ認証とエンティティ認証の決定的な違い（liveness）
- パスワード保存の仕組みと、実装で繰り返される失敗
- オフライン攻撃とオンライン攻撃で守り方が変わること、チャレンジレスポンスの暗黙の仮定

---

## データ認証とエンティティ認証は別物

```
データ認証:      「このメッセージは確かにその鍵の持ち主が作った」
                → 時間の概念がない。1年前のメッセージでも検証は通る
エンティティ認証: 「この相手は今この瞬間に応答している本人である」
                → liveness（生存性）の確認が本質
```

**なぜ区別が必要か**: 過去の正しい応答を記録して再送すれば、データ認証だけでは
「本人からのメッセージ」として通ってしまう（リプレイ攻撃）。エンティティ認証は
**セッションという時間的な枠**を持ち、「今」を確認する仕組みを必ず含む
（暗号の文献では *identification* と呼ぶことがあり、日常語とずれる）。

---

## 3つの要素

| 要素 | 例 | 主な失敗モード |
|---|---|---|
| **知っているもの** | パスワード・PIN | 漏洩・推測・使い回し |
| **持っているもの** | スマートカード・トークン・スマートフォン | 紛失・盗難・複製 |
| **であるもの** | 指紋・虹彩・顔 | **取り消せない**・複製されうる |

複数を組み合わせるのが多要素認証（MFA）だが、**同じ経路を通る要素を足しても強くならない**
（SMS のワンタイムコードは、端末を奪われれば独立な要素として機能しない）。

---

## パスワードの保存

パスワードは平文で保存してはならない。しかし単にハッシュするだけでも不十分である。

```
ソルト (salt) … 利用者ごとに異なるランダム値を連結してからハッシュする
低速ハッシュ   … bcrypt / scrypt / Argon2 / PBKDF2 など計算コストを意図的に高くした関数
```

### ソルトが防ぐもの

| ソルトなし | ソルトあり |
|---|---|
| 事前計算した表（レインボーテーブル）で一括照合できる | ソルトごとに計算し直す必要があり、事前計算が使えない |
| **同じパスワードの利用者が同じハッシュになる**ため相関が漏れる | 同じパスワードでも異なるハッシュになる |

2つ目が見落とされやすい。ソルトは総当たりを防ぐだけでなく**利用者間の相関を隠す**。

### 実装で繰り返される失敗

| 失敗 | なぜ意味がなくなるか |
|---|---|
| 機器のモデル番号をソルトにする | 同じ製品の全台が同じソルトになり、**個体ごとに異なる**という前提が崩れる |
| 推奨反復回数を大幅に下回る | 低速ハッシュの目的は計算コストの引き上げなので、防御力がそのまま落ちる |

**仕様どおりに実装したつもりでも、パラメータを甘くすれば防御は失われる。**

## オフライン攻撃とオンライン攻撃

守り方がまったく違うので、区別が要る。

| | オフライン攻撃 | オンライン攻撃 |
|---|---|---|
| 状況 | ハッシュ値を入手し、手元で試行する | 実際のシステムに認証を試みる |
| 試行回数 | **無制限**（攻撃者の計算資源だけが制約） | システムが制限できる |
| 守り方 | **鍵長・ハッシュのコスト**で守る | **レート制限・ロックアウト**で守る |

**この区別が PIN の設計を説明する。** 6桁の PIN は100万通りしかなくオフラインなら即座に破れるが、
実用されているのは**カードが試行回数を数えて数回で自ら止まる**からである。

ただし「1人3回まで」の制限が守るのは個人の口座だけである。
利用者が100万人いれば全体では300万回の試行機会があり、
**「誰か1人でも破れればよい」攻撃者には十分な回数**になる——
個人単位のレート制限は母集団全体への攻撃を止めない。

## チャレンジレスポンスと、その暗黙の仮定

liveness を確認する標準的な方法。

```
検証者 → 証明者: 毎回異なるランダム値（チャレンジ）を送る
証明者 → 検証者: 秘密鍵を使ってチャレンジに応答する
```

毎回チャレンジが変わるので**過去の応答を再送しても通らない**——リプレイ攻撃への対策になる。
秘密を明かさずに知識を示す形にすればゼロ知識証明になり、その定式化は
[`../../03_privacy/03_ppt-cryptographic/02_zero-knowledge-proofs.md`](../../03_privacy/03_ppt-cryptographic/02_zero-knowledge-proofs.md)
が本体（**認証には knowledge soundness が必要**という議論もそこにある）。

### 仮定①：証明者と検証者が近い

チャレンジレスポンスは「**両者が物理的に近い**」ことを暗黙に仮定している。
この仮定はプロトコルに書かれていないが、破られると成立しなくなる。

**リレー攻撃**は、正規のメッセージをそのまま中継するだけで認証を通す。
暗号は破られていない。無線での実例（車のキーレスエントリ）と対策の distance bounding は
[`../../06_systems-security/06_wireless-security.md`](../../06_systems-security/06_wireless-security.md) が本体。

### 仮定②：端末は正直である

決済で実証された例。カードと端末の間に入り、**端末には「PIN 検証は成功した」と見せ、
カードには「今日は PIN を検証しない」と伝える**中間者攻撃が成立した。
両者の認識が食い違ったまま取引が成立してしまう。

**プロトコルの各主体が「同じ事実を共有している」ことを保証しなければならない。**

### 仮定③：片方向認証を2回やれば相互認証になる

**ならない。** A が B を認証し、B が A を認証しても、
**2つが同じセッションに結び付いていなければ**、攻撃者が間に入って
それぞれ別の相手と認証を成立させられる。
相互認証は「同一セッションについて双方が相手を認証した」ことを要求し、
このセッションへの束縛（session binding）が抜けると中間者攻撃の余地が残る。

## 生体認証の本質的な限界

| 性質 | 帰結 |
|---|---|
| **取り消せない** | パスワードは変更できるが指紋は変更できない。一度漏れたら恒久的に使えない |
| 秘密ではない | 指紋は触った物に残り、顔は公開されている。**秘密を前提にできない** |
| 複製されうる | 型取りや高解像度画像から偽造物を作った実証例がある |

**生体情報は「鍵」ではなく「利便性のための識別子」として扱うのが妥当**である。
実務では端末内でローカルに検証し、その結果で端末内の秘密鍵の使用を許可する構成を取る
（生体情報自体をサーバに送らない）。法的な側面は [`../../07_legal/`](../../07_legal/index.md) の管轄。

## FIDO / パスキー：フィッシング耐性という設計

パスワードを置き換える標準。核心は**署名の対象にサイトのオリジンを含める**ことである。

```
サイトごとに異なる鍵ペアを作り、署名にオリジン（ドメイン）を結び付ける
        ↓
偽サイトに対しては偽サイト用の署名しか作れない
→ 利用者が騙されても、その認証情報は本物のサイトでは使えない
```

**「利用者が注意する」ことに依存しない**点が本質的な進歩である。
パスワードはどれだけ強くしても偽サイトに入力すれば漏れるが、
FIDO はその失敗モードを構造的に消している。
運用面（登録・復旧・紛失時の扱い）は
[`../../08_management-governance/02_security-operations.md`](../../08_management-governance/02_security-operations.md) を参照。

## 演習（解答つき）

1. データ認証とエンティティ認証の違いを、リプレイ攻撃を使って説明せよ。
2. 6桁の PIN が実用されている理由を、オフライン攻撃とオンライン攻撃の区別から述べよ。
   また「1人3回まで」の制限が守らないものは何か。
3. 「A が B を認証し、B が A を認証した」だけでは相互認証にならない理由を述べよ。

<details><summary>解答</summary>

1. データ認証は「このメッセージが正しい鍵で作られた」ことだけを保証するので、
   **過去の正しいメッセージを記録して再送すれば検証を通る**。エンティティ認証は
   「相手が今この瞬間に応答している」ことを確認する必要があり（liveness）、
   毎回異なるチャレンジを使うなどの仕組みで再送を排除する。
2. 6桁 PIN は100万通りしかなく、手元で試せる**オフライン攻撃**なら即座に破れる。
   実用されているのは、試行回数を数えて数回で停止する**オンライン攻撃**の状況に
   限定されているから。守らないのは**母集団全体への攻撃**——利用者100万人なら
   全体で300万回の機会があり、「誰か1人でも破れればよい」攻撃者には十分になる。
3. 2つの認証が**同一セッションに結び付いている保証がない**ため。攻撃者が間に入り、
   A には B のふりをし B には A のふりをすれば、それぞれの認証は成功しつつ
   A と B が直接通信していない状態を作れる。相互認証には
   「同じセッションについて双方が相手を認証した」という束縛が必要になる。

</details>
