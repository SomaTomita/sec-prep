# 04. Signal・EMV・Blockchain

> 親: [README](./README.md) ｜ 前: [03 TLS・IPsec・SSH](./03_tls-ipsec-ssh.md) ｜ 層: 基礎(Layer 1)

[03](./03_tls-ipsec-ssh.md) の3つはいずれも「オンラインで、相手と対話しながら」動くプロトコルだった。
ここで見る3つは**制約が違う**——相手がオフライン、ネットワークがない、中央機関がない。

**この1ページで分かること**

- 相手がオフラインでも鍵を確立する仕組みと、鍵をメッセージごとに更新する意味
- EMV の設計が「オフラインでも成立しなければならない」制約から導かれること
- プロトコルの形は暗号の選択ではなく**運用制約と脅威モデル**が決めること

---

## Signal Protocol — E2E 暗号化メッセージング

端末から端末まで暗号化し、中継サーバも中身を読めない方式。2つの仕組みを組み合わせる。

```
X3DH（Extended Triple Diffie-Hellman）:
  相手がオフラインでも、事前に公開しておいた鍵材料を使って初回の共有鍵を確立する
  X25519（Curve25519。→ ../03_public-key-crypto/03_ecc.md）ベース

Double Ratchet:
  メッセージを送るたびに新しい鍵を派生させ続ける「ラチェット」機構
```

### 制約が設計を決めている

**メッセージングの制約は「相手が今いない」こと**である。
[03](./03_tls-ipsec-ssh.md) の TLS は双方が同時にオンラインである前提で鍵交換したが、
メッセージングではそれが成立しない。

```
TLS:    双方が対話して ECDHE で鍵を確立する（同時にオンライン）
X3DH:   相手が事前にサーバへ預けた鍵材料を使う（相手はオフラインでよい）
```

### Double Ratchet が達成する2つの性質

| 性質 | 内容 |
|---|---|
| **前方秘匿性** | 現在の鍵が漏れても、**過去**のメッセージは復号できない |
| **事後侵害安全性** (post-compromise security) | 一時的に状態を奪われても、その後の会話は**自己修復**して安全になる |

2つ目が Signal の特徴である。[02](./02_key-management.md) で見た前方秘匿性は
「過去を守る」性質だったが、こちらは**未来を取り戻す**性質になる。

```
攻撃者が端末の状態を完全に奪った
        ↓ しかし利用者が使い続けると
毎メッセージで新しい鍵材料が混ざり続ける
        ↓
攻撃者は追随できなくなり、やがて読めなくなる
```

単発の DH（[`../03_public-key-crypto/02_dh.md`](../03_public-key-crypto/02_dh.md)）の
前方秘匿性を**メッセージ単位に細分化した発展形**と理解できる。

> ⚠️ **限界**: 端末にマルウェアが常駐して平文を読み続けている場合、
> この性質は助けにならない。守れるのは「鍵材料を一度奪われた」ケースである。

## EMV（IC カード決済）— オフラインでの真正性検証

```
目的: ネットワーク接続なしでもカードの真正性・データ改ざんを検証する
SDA（Static Data Authentication）:  カードの静的データに発行会社が RSA 署名 → クローン防止は弱い
DDA（Dynamic Data Authentication）: 端末の乱数にカード自身が RSA 署名 → クローン耐性あり
CDA（Combined DDA）:                DDA に取引データも結びつけて署名 → 最も強い
```

いずれも [`../03_public-key-crypto/01_rsa/`](../03_public-key-crypto/01_rsa/README.md) の
署名検証をベースに、発行会社 → カードという**階層的な公開鍵基盤**で構築されている。

### なぜ EMV はこの形なのか：オフライン制約

**設計を理解する鍵は「通信が使えない場面でも決済が成立しなければならない」**という運用制約にある。
機内・地下・回線障害でも支払いは行われる。この制約が次を強制する。

| 制約 | 帰結 |
|---|---|
| 発行者に問い合わせられない | **カード自身が真正性を証明**する必要がある → カードに秘密鍵と証明書を載せる |
| 端末は発行者を直接信頼できない | **証明書階層**（スキーム → 発行者 → カード）が要る |
| 端末側が改造されうる | 端末の言うことをカードが鵜呑みにしてはいけない（→ [01](./01_entity-authentication.md) の PIN バイパス） |
| カードは電源も計算力も乏しい | 軽い演算と短いメッセージに収める必要がある |

**TLS と比較すると設計思想の違いがはっきりする。**
TLS はオンライン前提なので失効確認も鍵合意もその場でできる。
EMV はそれができないので、**事前に配った証明書とカード内の秘密鍵**に頼る。

> **一般的な教訓**: プロトコルの形は暗号方式の選択ではなく、
> **運用制約と脅威モデル**から決まる。SDA/DDA/CDA という3段階も
> 「どこまでのコストを払えるか」という制約の反映である。

## Blockchain（Bitcoin を例に）— 分散台帳

```
所有権の証明: ECDSA（secp256k1 曲線。→ ../03_public-key-crypto/04_digital-signatures.md）で取引に署名
改ざん検知:   各ブロックが前ブロックのハッシュを含む「ハッシュチェーン」（→ ../04_hash-and-mac.md）
             取引は Merkle 木にまとめられ、木のルートだけがブロックヘッダに入る
合意形成:     Proof of Work — 計算資源を消費した証明で改ざんコストを上げる
```

**制約は「中央機関が存在しない」こと**である。
[02](./02_key-management.md) の KDC も [03](./03_tls-ipsec-ssh.md) の CA も、
信頼できる中央を前提にしていた。それを外すと何が必要になるかを示した設計と言える。

2008年の Nakamoto の論文が起点で、中央機関なしに
「誰が何を所有しているか」を暗号プリミティブの組み合わせだけで実現した点が新規性だった。

> 二重支払い問題からの導出、PoW/PoS の比較、トリレンマは
> [`../../06_systems-security/05_distributed-systems-security.md`](../../06_systems-security/05_distributed-systems-security.md) が本体。
> ここでは**暗号プリミティブの組み合わせ**という視点にとどめる。

---

## 3つを並べて見える構造

| プロトコル | 外した前提 | 代わりに導入したもの |
|---|---|---|
| Signal | 相手が同時にオンライン | 事前公開の鍵材料（X3DH） |
| EMV | ネットワークが使える | カード内の秘密鍵と証明書階層 |
| Blockchain | 信頼できる中央機関 | 計算資源による合意（PoW） |

**どれも「当然の前提」を1つ外し、その代償を暗号で埋めている。**
プロトコル設計を読むときは「**この設計は何を前提にしていないのか**」を問うと構造が見える。

## 演習（解答つき）

1. X3DH が TLS の鍵交換と違う形を採らなければならなかった理由を述べよ。
2. EMV の SDA が「クローン防止には弱い」とされる理由を述べよ。
3. Signal の Double Ratchet が持つ事後侵害安全性は、どのような攻撃には無効か。

<details><summary>解答</summary>

1. TLS は**双方が同時にオンライン**である前提で、対話しながら ECDHE で鍵を確立する。
   しかしメッセージングでは相手がオフラインのことが普通であり、対話ができない。
   X3DH は相手が事前にサーバへ預けておいた鍵材料を使うことで、
   **相手の応答を待たずに**初回の共有鍵を確立できるようにしている。
2. SDA はカードの**静的**データに対する署名を検証するだけで、
   カードとの対話（チャレンジ・レスポンス）を伴わない。
   したがって署名済みデータをそのままコピーした偽造カードでも検証を通過してしまう。
   DDA/CDA は端末が出す乱数にカード自身が署名するため、
   データのコピーだけでは応答を作れない（[01](./01_entity-authentication.md) の liveness の確認）。
3. **端末にマルウェアが常駐し、平文を継続的に読み取っている場合には無効**である。
   事後侵害安全性が守るのは「鍵材料を一度奪われた」ケースで、
   その後は新しい鍵材料が混ざることで攻撃者が追随できなくなる。
   しかし攻撃者が端末内で平文そのものを読み続けられるなら、
   鍵がいくら更新されても意味がない。

</details>
