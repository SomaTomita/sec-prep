# 02. ブロック暗号の設計思想

> 親: [README](./README.md) ｜ 前: [01 ストリーム暗号と LFSR](./01_stream-ciphers-and-lfsr.md) ｜ 次: [03 AES の内部構造](./03_aes-internals.md) ｜ 層: 基礎(Layer 1)

ストリーム暗号は「鍵から長い乱数列を作る」問題だった。
ブロック暗号は逆に、**固定長のブロックそのものを可逆な形で混ぜ合わせる**。
この節では、その発想がどこから来たのかを歴史的な系譜でたどる。

**この1ページで分かること**

- 換字暗号の弱点（頻度分析）が「コードブック」という発想を生んだ経緯
- Shannon の「拡散と混同」という2つの性質と、それを反復で実現する理由
- Feistel と SPN という2つの可逆構造の違い

---

## 換字暗号 → 頻度分析 → コードブック

古典的な換字暗号（1文字を別の1文字に置き換える）は、**言語の統計的偏り**に弱い。
英語なら `e` が最も出現するといった頻度情報から、置換表そのものが復元できる
（頻度分析）。

この弱点への対策として生まれた発想が**コードブック**——
1文字ではなく、まとまった単位（単語や句）ごとに全く無関係な符号に置き換える表である。
単位が大きくなるほど頻度の偏りは薄まる。

### アルゴリズム的コードブック

しかし本物のコードブックには限界がある。**あらゆる入力に対応する表を事前に用意し、
安全に配布・管理する**のは非現実的である。

ブロック暗号はこの発想を「表を持ち歩く」代わりに
**「鍵から表を計算するアルゴリズム」**に変える。固定長ブロック（例: 128ビット）の
入力それぞれに対して、鍵ごとに異なる出力を**計算で**割り当てる——
これは事実上「鍵の数だけコードブックがある」ことと同じであり、
かつ表を保存・配布する必要がない。

```
理想:   ブロック暗号 = 鍵ごとに異なる「ランダムな置換」を計算で実現する関数
現実:   完全にランダムな置換に「計算量的に区別できない」ことを目指す
```

「完全にランダムではなく、ランダムと見分けがつかない」という発想が
PRP（Pseudorandom Permutation）の定義であり、詳細な形式的定義は
Coursera Crypto I 講義ノート（`courses/coursera-crypto1/04_block-ciphers/`）が本体。

## Shannon の交互適用：拡散と混同

Claude Shannon は、暗号が備えるべき性質を2つに整理した。

```
拡散 (diffusion): 平文の1ビットを変えると、暗号文の多くのビットが変わる
                  （統計的な偏りを暗号文全体に薄く広げる）
混同 (confusion): 鍵と暗号文の関係を複雑にし、単純な代数関係で結べなくする
```

**どちらか一方だけでは不十分。** 混同だけでは局所的な偏りが残り、
拡散だけでは鍵の影響が薄まりすぎて安全な非線形性が確保できない。

Shannon はこの2つを**交互に繰り返し適用する**ことを提案した。
パン生地をこねる作業に例えられる——一度こねただけでは具材は均一に混ざらないが、
「延ばして畳む」を何度も繰り返すと、局所的な操作の積み重ねが全体の均一な混合を生む。

```
ラウンド関数（拡散+混同の1回分）を r 回繰り返す = 反復暗号（iterated cipher）
```

1回のラウンド関数は単純で解析しやすくてよい。**ラウンド数を重ねることで、
全体としての複雑さが安全性を生む**——これが AES を含む現代のブロック暗号に共通する設計思想である。

## 可逆性をどう保証するか：Feistel 構造

ラウンド関数それ自体は非線形で複雑であってよいが、暗号化した以上は
**復号できなければならない**。つまりラウンド関数全体が可逆(全単射)である必要がある。

Feistel 構造は、**中身の関数 F が可逆でなくてもよい**という工夫でこれを解決する。

```
入力ブロックを左右 (L, R) に分割
各ラウンド:
    L' = R
    R' = L XOR F(R, ラウンド鍵)
```

**F が何であっても、この変換は必ず可逆になる。** 復号は同じ構造を逆順にたどるだけでよい
（`L = R' XOR F(L', ラウンド鍵)`, `R = L'`）。

F の中身を安全性の証明対象から外し、**「F が何であれ構造全体は可逆」**という
数学的な保証だけで復号可能性を切り離せる点が Feistel の強みである。
DES はこの構造を採用した（詳細は下記）。

---

## もう一つの選択肢：SPN 構造

SPN（Substitution-Permutation Network）は逆に、
**各段階そのものを可逆な演算だけで組み立てる**。

```
S-box (Substitution): 小さなブロック単位で非線形な換字を行う（可逆な換字表）
P-box / 線形変換 (Permutation): ビットやバイトの位置を並べ替え・線形混合する
```

S-box 自体が可逆な置換であり、線形変換も可逆であるため、
**各層を逆順にたどれば全体が復号できる**。Feistel のように
「半分だけ変換して残り半分と XOR する」という迂回が要らない。

### Feistel vs SPN

| | Feistel | SPN |
|---|---|---|
| ラウンド関数の可逆性 | **不要**（構造が可逆性を保証） | **各層が可逆である必要がある** |
| 1ラウンドあたりの拡散 | 半分のブロックにしか及ばない | ブロック全体に及びやすい |
| 代表例 | DES, Blowfish | AES, Serpent |
| 暗号化と復号の回路 | ほぼ共通化できる | 逆変換の実装が別途必要なことが多い |

**どちらが優れているという設計ではなく、トレードオフの選び方が違う。**
Feistel は非線形関数の設計自由度が高く、SPN は少ないラウンド数で
ブロック全体への拡散を達成しやすい。AES が SPN を選んだ理由は
[03](./03_aes-internals.md) で見る。

---

## DES と 3DES：この系譜の実例（要点のみ）

- **DES**（1977年, FIPS 46）: Feistel 構造・56bit 鍵・16ラウンド。
  鍵長が短く総当たりに敗れた。
- **3DES**: DES を3回鎖状に適用し実効鍵長を伸ばした延命策。処理が遅く、
  64bit ブロック長に起因する Sweet32 攻撃の対象にもなった。

破られ方の詳細（差分解読・線形解読への耐性の低さ、鍵スケジュールの弱点)・総当たりのコスト計算は
Coursera Crypto I 講義ノート（`courses/coursera-crypto1/04_block-ciphers/`）が本体。
ここで押さえるべきは1点——**Feistel 構造自体の欠陥ではなく、鍵長とブロック長という
パラメータの選択が時代遅れになった**という教訓である。構造の選択とパラメータの選択は別問題であり、
AES はこの反省から SPN 構造と可変鍵長（128/192/256bit）を選んだ。

## 演習（解答つき）

1. 「コードブックをアルゴリズムで代替する」という発想が解決した問題は何か。
2. Feistel 構造で、ラウンド関数 F 自体が可逆である必要がないのはなぜか。
3. SPN 構造が Feistel 構造と比べて「各層が可逆でなければならない」制約を持つ理由を述べよ。

<details><summary>解答</summary>

1. 本物のコードブックは、あらゆる入力に対応する対応表を事前に用意し、
   安全に配布・保管する必要があり非現実的だった。鍵からアルゴリズムで表を
   計算することで、表そのものを保存・配布する必要をなくし、
   かつ鍵ごとに異なる「事実上のコードブック」を持てるようにした。
2. Feistel 構造は `L' = R, R' = L XOR F(R, k)` という形を取り、復号時には
   `R' XOR F(L', k)` によって `L` を、`L'` によって `R` を復元できる。
   この復元の手順は F 自体を逆に計算することを一切要求しない——
   F は一方向にしか計算されず、構造の対称性だけで可逆性が保証されるため。
3. SPN には Feistel のような「半分を素通りさせて残り半分とだけ混ぜる」迂回がなく、
   S-box や線形変換がブロック全体に直接作用する。復号するには、暗号化で使った
   各変換（S-box、線形変換）をそれぞれ逆向きに計算する必要があるため、
   個々の構成要素自体が可逆でなければならない。

</details>
