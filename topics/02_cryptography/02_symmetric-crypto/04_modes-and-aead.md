# 04. モードと AEAD

> 親: [README](./README.md) ｜ 前: [03 AES の内部構造](./03_aes-internals.md) ｜ 次: [05 ブロック暗号からハッシュへ](./05_hashing-from-block-ciphers.md) ｜ 層: 基礎(Layer 1)

AES は1ブロック（128bit）を暗号化する関数でしかない。実際のメッセージは
複数ブロックにまたがる。同じ鍵で複数ブロックを**安全に**暗号化する規則が「モード」であり、
さらに機密性だけでは不十分で完全性も要る場面が AEAD を生んだ。

**この1ページで分かること**

- モードとは「安全性証明の仮定を守るための使い方の規則」であること
- CBC のバースデー境界が「なぜ 2^(n/2) ブロックで危険になるか」の数学的な理由
- CCM/OCB/GCM という3つの AEAD 方式の違い

---

## モードとは何か

ブロック暗号は決定論的な関数である。同じ鍵で同じブロックを暗号化すれば、
常に同じ暗号文になる——これは [01](./01_stream-ciphers-and-lfsr.md) で見た
「同じキーストリームの再利用」と同型の危険を生む。

モードは、この決定論性を安全に使うための**追加の規則**——
毎回異なる入力をブロック暗号に与える仕組みである。
[01](./01_stream-ciphers-and-lfsr.md) の原理がここでも成り立つ：
**乱数性（ランダムな IV）か状態性（カウンタ）のどちらかが必要**。

---

## ECB：モードとして失格

各ブロックを鍵だけで独立に暗号化する。**IV もカウンタも使わない**ため、
同じ平文ブロックは常に同じ暗号文ブロックになる——これは決定論的暗号化そのものであり、
[`../03_public-key-crypto/05_security-definitions-and-kem.md`](../03_public-key-crypto/05_security-definitions-and-kem.md) の
「決定論的な暗号化は即座に IND-CPA を破る」がそのまま対称鍵側でも成り立つ。
ECB で暗号化した画像がシルエットとして判読できてしまう例がこれを可視化する。

---

## CBC：連鎖で決定論性を壊す

```
C_0 = IV
C_i = Enc(k, P_i XOR C_{i-1})
```

各ブロックの暗号化前に、直前の暗号文ブロックと XOR することで、
同じ平文ブロックでも文脈（それ以前の内容）が違えば異なる暗号文になる。
**IV はランダムかつ予測不能である必要がある**——IV が予測できると、
攻撃者は次に来る平文を推測して事前に XOR 差分を仕込めてしまう
（BEAST 攻撃はまさにこの隙を突いた）。

### バースデー境界の導出

CBC はブロック暗号を PRP（ランダムな置換）とみなして安全性を証明するが、
**「ランダムな置換」は「ランダムな関数」とは違う**——衝突が起きない
（全単射である）という制約がある。この違いが、長く使うと安全性が崩れる原因になる。

```
n bit ブロックで q 個の暗号文ブロックを作ると、
それらが「真にランダムな関数の出力」から区別できてしまう確率は、
おおよそ q^2 / 2^(n+1) のオーダーで増加する（バースデーの逆説と同じ数学）
```

これはバースデーパラドックス（「同じ誕生日のペアが生じる確率は参加人数の**2乗**で
効いてくる」、[`../../01_prerequisites/04_networks-probability/03_probability-statistics.md`](../../01_prerequisites/04_networks-probability/03_probability-statistics.md)）
と同一の数学的構造による。ブロックの出力が衝突すると（`C_i = C_j`）、対応する
`P_i XOR C_{i-1} = P_j XOR C_{j-1}` が成り立ち、XOR を取ることで平文ブロック同士の関係が漏れる。

```
n = 64bit（DES, 3DES, Blowfish）→ 2^32 ブロック ≈ 32GB で危険域
n = 128bit（AES）             → 2^64 ブロック（実務上まず到達しない）
```

**64bit ブロック暗号を TLS/VPN で長時間使うと、この境界に現実的に到達する**——
これが Sweet32（2016年）の指摘であり、[02](./02_block-cipher-architecture.md) で
触れた 3DES 廃止の直接の理由の一つになっている。

### CBC パディングオラクル

CBC は固定長ブロックを要求するため、最終ブロックにパディングが要る。
**復号時にパディングの妥当性を外部から観測できると**、
[`../03_public-key-crypto/05_security-definitions-and-kem.md`](../03_public-key-crypto/05_security-definitions-and-kem.md) で見た
「復号オラクル」がそのまま実現し、鍵を知らずに平文を1バイトずつ復元できてしまう
（POODLE 攻撃はこの一例）。**エラーの有無という1ビットの情報漏洩だけで暗号が崩れる**——
これも CCA2 安全性が実務でなぜ必要とされるかを裏付ける実例である。

---

## CTR：ブロック暗号をストリーム暗号に変える

```
Keystream_i = Enc(k, Nonce || Counter_i)
C_i = P_i XOR Keystream_i
```

ブロック暗号の出力そのものを暗号化せず、**キーストリーム生成にだけ使う**。
これは [01](./01_stream-ciphers-and-lfsr.md) のストリーム暗号の構図そのもの——
「状態（カウンタ）」で乱数性の要件を満たしている。

暗号化と復号が同一処理になる、並列化できる、パディングが不要、といった利点がある。
**ただし nonce の再利用は致命的**——同じ nonce で2回暗号化すると同じキーストリームが
再利用され、[01](./01_stream-ciphers-and-lfsr.md) の鍵ストリーム再利用の破局がそのまま起こる。

---

## なぜ機密性だけでは足りないのか

CBC も CTR も、**機密性**（内容を読めなくする）は提供するが**完全性**
（改ざんされていないことの保証）は提供しない。CTR では暗号文の特定バイトを
XOR で書き換えるだけで、対応する平文の同じ位置を狙って変更できてしまう——
攻撃者は内容を読めなくても、意味のある改ざんができる。

CBC パディングオラクルも同根——復号側が「パディングが壊れている」ことを検出できてしまうのは、
暗号文の改ざんに対して何のチェックもしていないためである。
**機密性と完全性は別の性質であり、両方が必要**——この認識が AEAD を生んだ。

---

## AEAD という単一概念

AEAD（Authenticated Encryption with Associated Data）は、
**暗号化と MAC 相当の認証を1つの操作にまとめる**。

```
Enc(k, N, P, AD) → (C, T)     N: nonce, AD: 平文にしないが認証はしたいデータ, T: 認証タグ
Dec(k, N, C, AD, T) → P か ⊥   タグ検証に失敗すれば ⊥（復号結果を一切返さない）
```

AD（Associated Data）が重要——例えばパケットのヘッダは**暗号化はしたくないが
改ざんは検出したい**。AD 部分は認証の対象に含めつつ暗号化はしない、
という使い分けができる。

### CCM / OCB / GCM の比較

| | CCM | OCB | GCM |
|---|---|---|---|
| 構成 | CTR + CBC-MAC（2パス） | 専用の1パス構成 | CTR + GHASH（1.5パス、並列化可） |
| 速度 | 遅い（暗号化と MAC を別々に計算） | 最速（1パス） | 高速（GHASH は並列計算可能） |
| nonce 再利用時の被害 | 深刻（鍵回復につながりうる） | 深刻 | **特に深刻**（認証鍵 H が漏れ、偽造が可能になる） |
| 採用状況 | Wi-Fi (WPA2/3), Bluetooth LE | 特許問題の歴史ありライセンス整理後普及限定的 | **TLS 1.3, IPsec で主流** |
| 標準 | NIST SP 800-38C | RFC 7253 | NIST SP 800-38D |

**GCM が最も広く使われる**のは、CTR ベースで並列化・ハードウェア支援
（AES-NI との相性）に優れるため。ただし GCM は nonce 再重複に対して
とりわけ脆く、**同じ鍵・nonce の組を二度使うと認証鍵が計算できてしまい、
以降の暗号文を自由に偽造できる**——nonce 管理の重要性がここでも繰り返される。

### タグ長は鍵長より短くてよい

認証タグは通常 128bit ではなく **96bit や 64bit** に切り詰めて使われる
（GCM の既定は 96bit）。鍵の総当たりが `2^鍵長` 回の探索を要するのに対し、
タグの偽造は「1回の送信で `2^(-タグ長)` の確率で通ってしまう」という
確率的な当てずっぽうであり、両者は異なる種類の安全性——**偽造の成功確率を
どこまで許容するか**という運用上のトレードオフでタグ長は選ばれる。

---

## 演習（解答つき）

1. ECB が「モードとして失格」とされる理由を、決定論的暗号化の観点から述べよ。
2. 64bit ブロック暗号（3DES）を長時間の TLS 接続で使うと危険な理由を、
   バースデー境界の数式を使って説明せよ。
3. GCM で nonce を再利用した場合の被害が、CTR 単体での nonce 再利用より深刻なのはなぜか。

<details><summary>解答</summary>

1. ECB は IV もカウンタも使わず、鍵だけで各ブロックを独立に暗号化する。
   同じ平文ブロックは常に同じ暗号文ブロックになるため、これは決定論的暗号化そのものであり、
   平文の繰り返しパターン（構造）が暗号文にそのまま透けて見えてしまう。
2. バースデー境界はおおよそ `q^2 / 2^(n+1)` のオーダーで衝突確率が増加する。
   `n=64` の場合、`q ≈ 2^32` ブロック（約32GB）付近で衝突確率が無視できなくなる。
   長時間の TLS 接続はこの量のデータを現実的にやり取りしうるため、
   ブロックの衝突から平文ブロック同士の XOR 関係が漏れる危険域に入る。
3. GCM の認証は GHASH が使う認証鍵 H に依存しており、H は nonce ごとに導出される
   キーストリームの一部から間接的に得られる。同じ鍵・nonce で2回暗号化すると、
   2つの暗号文から H を計算で求められてしまい、以降**任意の暗号文に対して
   正しく検証が通るタグを偽造できる**——機密性の破綻（CTR と同型）に加えて、
   完全性の保証そのものが失われる点が単なる CTR の nonce 再利用より深刻である。

</details>
