# 03. AES の内部構造

> 親: [README](./README.md) ｜ 前: [02 ブロック暗号の設計思想](./02_block-cipher-architecture.md) ｜ 次: [04 モードと AEAD](./04_modes-and-aead.md) ｜ 層: 基礎(Layer 1)

[02](./02_block-cipher-architecture.md) で見た SPN 構造の実例として、AES の内部を
1段ずつ見る。それぞれの変換には、なぜその形なのかという数学的な根拠がある。

**この1ページで分かること**

- AES 選定の経緯と、ブロック長・鍵長・ラウンド数の関係
- 4つの変換（SubBytes/ShiftRows/MixColumns/AddRoundKey）それぞれの役割
- MDS 行列と分岐数という「拡散の強さ」を測る指標

---

## 経緯とパラメータ

DES の後継を選ぶ NIST の公募（AES コンペティション, 1997–2000年）で、
Joan Daemen と Vincent Rijmen による **Rijndael** が選ばれ、2001年に FIPS 197 として標準化された。

```
ブロック長: 128bit 固定
鍵長:      128 / 192 / 256bit（それぞれ AES-128 / AES-192 / AES-256）
ラウンド数: 鍵長に応じて 10 / 12 / 14
```

> Rijndael 自体はブロック長 128/192/256bit を選べる設計だったが、
> AES として標準化されたのはブロック長 128bit のみ。より広いブロック長・鍵長を持つ
> **Rijndael-256** の標準化提案が2024年12月に NIST へ提出され、コメント募集の段階にある
> （2026年時点でまだ最終標準化はされていない）。断定せず「議論が進行中」と理解しておく。

---

## 状態を 4×4 バイト配列として見る

AES は128bitの入力を、**4行4列のバイト配列**（状態, State）として扱う。
以降の4つの変換はすべて、この配列に対する操作として定義される。

```
バイト列 → 4×4 配列（列優先で埋める）
s00 s01 s02 s03
s10 s11 s12 s13
s20 s21 s22 s23
s30 s31 s32 s33
```

1ラウンドは次の4つの変換を順に適用する（最終ラウンドのみ MixColumns を省く）。

```
SubBytes → ShiftRows → MixColumns → AddRoundKey
```

[02](./02_block-cipher-architecture.md) の言葉で言えば、SubBytes が**混同**、
ShiftRows と MixColumns が**拡散**を担う。

---

## SubBytes：非線形性の源

各バイトを、固定の 256 エントリの表（S-box）を通して別のバイトに置き換える。
この表は思いつきではなく、2段階の数学的手続きで作られている。

```
① GF(2^8) 上での乗法逆元を取る（0 は特別に 0 に写す）
② その結果にアフィン変換（GF(2) 上の線形変換 + 定数の加算）を適用する
```

**乗法逆元だけでは不十分な理由**——逆元を取る操作は代数的に単純すぎ、
そのままでは代数的な関係式（線形近似・アフィン近似）が作りやすく、
差分解読・線形解読に弱くなる。アフィン変換を重ねることで、
この単純な代数構造を隠し、**線形近似・差分特性の確率をともに最小化**している
（S-box の設計基準の詳細な数値的評価は `deep/differential-linear-cryptanalysis/` に委ねる）。

GF(2^8) 上の演算そのものの手計算は
[`../../01_prerequisites/01_math-for-crypto/02_groups-rings-fields/06_gf2n-and-aes.md`](../../01_prerequisites/01_math-for-crypto/02_groups-rings-fields/06_gf2n-and-aes.md) が本体。

---

## ShiftRows：列だけでは足りない拡散

4行それぞれを、行番号に応じた分だけ**巡回シフト**する（0行目はシフトなし、
1行目は1バイト、2行目は2バイト、3行目は3バイト）。

```
シフト前            シフト後
s00 s01 s02 s03     s00 s01 s02 s03
s10 s11 s12 s13  →  s11 s12 s13 s10
s20 s21 s22 s23     s22 s23 s20 s21
s30 s31 s32 s33     s33 s30 s31 s32
```

**なぜ必要か**——MixColumns（次項）は「列」単位でしか混合しない。
ShiftRows がなければ、各列は常に同じ4バイトの集合のまま処理され続け、
**列同士が独立したまま**になってしまう。行をずらしてから列を混ぜることで、
1ラウンドのうちに状態全体（全16バイト）に影響が波及する。

---

## MixColumns：MDS 行列と分岐数

各列（4バイト）を、GF(2^8) 上で固定の 4×4 行列と掛け合わせて別の4バイトに変換する。
この行列は**適当な行列ではなく MDS 行列**（Maximum Distance Separable）——
符号理論から借りた概念で、**最大の拡散効率**を持つことが保証された行列である。

```
分岐数 (branch number) = 入力の非ゼロバイト数 + 出力の非ゼロバイト数 の最小値
```

MDS 行列を使うと、AES の MixColumns の分岐数は **5**（4バイトの列に対する理論上の最大値）
になる。**入力側で1バイトだけ変化させても、出力側は最低4バイト変化する**——
1バイトの変化が高々3バイトの変化にしかならないような「弱い」線形変換を排除する設計である。
分岐数が大きいほど、差分解読で必要なアクティブS-box数が増え、攻撃コストが跳ね上がる。

---

## AddRoundKey：唯一、鍵が混ざる場所

状態全体と、その時点のラウンド鍵とを単純に XOR する。

```
State = State XOR RoundKey
```

**4つの変換のうち、鍵が直接関わるのはここだけ**である。
SubBytes・ShiftRows・MixColumns は鍵に依存しない固定の変換であり、
鍵の情報は AddRoundKey を通じてラウンドごとに注入される
（各ラウンド鍵は元の鍵から鍵スケジュールで導出される）。

> Rijndael の設計文書は、GF(2^8) の構造をトーラス（円環）上の幾何として説明する余談を含むが、
> これは実装や安全性の議論には影響しない直感的な補助説明にとどまる。

## 実装と安全性

- **AES-NI**: 多くの CPU が SubBytes/ShiftRows/MixColumns を専用命令で実行し、
  ソフトウェア実装より高速かつ**タイミングサイドチャネルに強い**
  （テーブル参照によるキャッシュタイミング攻撃を避けられる）。
  サイドチャネル一般は [`../../04_hardware-security/04_side-channels/README.md`](../../04_hardware-security/04_side-channels/README.md) が本体。
- 総当たりのコスト、鍵スケジュールの詳細な安全性証明は
  Coursera Crypto I 講義ノート（`courses/coursera-crypto1/04_block-ciphers/05_aes.md`）が本体。

## 演習（解答つき）

1. SubBytes が「乗法逆元を取る」だけでなく「アフィン変換」も重ねているのはなぜか。
2. ShiftRows がなければ、MixColumns だけでは拡散がどう不十分になるか。
3. MDS 行列によって MixColumns の分岐数が 5 になることの意味を説明せよ。

<details><summary>解答</summary>

1. 乗法逆元を取るだけの変換は代数的に単純すぎ、線形近似・アフィン近似が
   作りやすい。これは差分解読・線形解読の突破口になる。アフィン変換を重ねることで
   この単純な代数構造を隠し、線形近似・差分特性の確率を最小化している。
2. MixColumns は列単位（同じ列の4バイト)でしか値を混合しない。ShiftRows がなければ
   各列は常に元のまま同じ4バイトの集合であり続け、列同士が混ざらない。
   結果として、ある列の変化がラウンドを重ねても他の列に波及せず、
   状態全体への拡散が起こらない。
3. 分岐数5は「入力の非ゼロバイト数+出力の非ゼロバイト数」の最小値が5であることを意味し、
   4バイトの列に対する理論上の最大値である。これは入力側で1バイトだけ変化させても、
   出力側は最低4バイトすべてが変化することを保証する。差分解読で辿れる「アクティブな
   バイト数」が最大化されるため、攻撃者が追跡できる差分パスの確率を最小化できる。

</details>
