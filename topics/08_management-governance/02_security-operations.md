# 02. 運用管理・IAM・BCP/DR・サードパーティリスク

> 前: [01 リスク管理フレームワーク](./01_risk-management.md) ｜ 次: [03 認証制度とセキュリティ経済学](./03_certification-economics.md) ｜ 層: 基礎(Layer 1)

**この1ページで分かること**

- IAM の 3 要素（認証・認可・記録）とアクセス制御の設計原則
- BCP と DR の関係（DR は BCP の部分集合）と、復旧目標を測る RTO/RPO
- サードパーティ（外部委託先）リスク管理の骨格と、マルチクラウドで統制が壊れる仕組み

[01](./01_risk-management.md) で評価したリスクを、日常運用で**低減・移転**する 3 本の柱を見る。

## 最小の例：深夜のアラート 1 件

```
02:13  監視ツール: 「経理 A のアカウントが海外 IP から社内サーバへログイン」
02:15  当番が確認: A は退職済み。だが ID が残っていた（IAM の穴）
02:20  即時対応: アカウント無効化・当該サーバを隔離
翌朝   復旧: バックアップから前日 23:00 の状態へ戻す（データ損失 3 時間 = RPO）
       業務再開は 09:00（停止 7 時間 = RTO）
```

この 1 件に IAM（誰が入れるか）・DR（どう戻すか）・サードパーティ（監視ツールは外部 SaaS）が全部出てくる。

## IAM（Identity and Access Management）

「本人確認」と「権限付与」を分けて考えるのが出発点。3 要素（AAA）:

| 要素 | 問い | 手段 |
|---|---|---|
| Authentication（認証） | あなたは誰か？ | パスワード・生体認証・MFA（多要素認証＝2 種類以上の証拠を要求） |
| Authorization（認可） | 何をしてよいか？ | 権限の割り当て |
| Accounting（記録） | 何をしたか？ | 監査ログ |

「ログインできる（認証済み）」と「その操作が許されている（認可済み）」は別の判断。

### アクセス制御の設計原則

| 原則 | 意味 |
|---|---|
| 最小権限 (Least Privilege) | 業務に必要な最小限の権限だけ |
| Need-to-know | 知る必要がある情報にだけアクセスを許す |
| 職務分離 (Separation of Duties) | 重要な操作を 1 人で完結できないよう分割 |

権限モデルは **RBAC**（役割単位で権限をまとめる）が最も一般的。部署・時刻・場所などの属性で判定する **ABAC** は大規模組織向け。

米国では NIST SP 800-63「Digital Identity Guidelines」が実装仕様を与える（IAL/AAL/FAL＝身元確認・認証器・連携の 3 種の保証レベル）。2025 年 8 月の **Rev. 4** でフィッシング耐性 MFA・パスキー対応が入った。

## BCP（事業継続計画）と DR（災害復旧）

| | BCP | DR |
|---|---|---|
| 目的 | 組織の「重要な事業機能」を災害中も継続 | IT システム・データを復旧 |
| 範囲 | 代替オフィス・代替要員・代替業務まで | BCP の一部。IT 面の技術的手段に限定 |

**DR は BCP の部分集合。** 成熟度は **ISO 22301:2019**（事業継続の国際標準）・**NIST SP 800-34 Rev. 1**（米連邦向け）で規定。

### RTO と RPO：復旧目標の 2 軸

```mermaid
flowchart LR
    B["最後のバックアップ"] -->|"RPO: 失ってよいデータの幅"| F["障害発生"]
    F -->|"RTO: 止まってよい時間"| R["復旧完了"]
```

| 指標 | 意味 | 冒頭の例 |
|---|---|---|
| RTO (Recovery Time Objective) | 障害から復旧までに許せる最大時間 | 7 時間 |
| RPO (Recovery Point Objective) | 許せる最大データ損失（時間換算） | 3 時間 |

RTO・RPO が短いほど冗長化・バックアップ頻度のコストは増える。[01](./01_risk-management.md) のリスク × コストがそのまま現れる。

## サードパーティリスク管理

クラウド・SaaS（ネット経由で使うソフト）・委託開発が一般化し、直接統制できない外部の水準が自組織のリスクになる。**NIST SP 800-161 Rev. 1**（C-SCRM＝サイバー供給網リスク管理、2022 年 5 月）が体系化。

| 典型例 | 何が起きるか |
|---|---|
| 委託先経由のマルウェア混入 | ソフトウェアサプライチェーン攻撃 |
| 委託先の事故 | 委託元データの漏洩 |
| 委託先の事業停止 | 自組織サービスの停止 |

対策は「契約前のデューデリジェンス（監査・認証確認）」＋「契約後の継続モニタリング」。GDPR の処理者契約（第 28 条）は [`../03_privacy/06_law-and-dpia.md`](../03_privacy/06_law-and-dpia.md)。

### 複数クラウドで統制はどう壊れるか

マルチクラウドは戦略というより部門ごとの導入の積み重ね。生じるのは新種の攻撃ではなく**統制の分断**。

| 分断する対象 | 何が起きるか |
|---|---|
| ID 管理 | 環境ごとに別の ID ストア。**退職者のアカウントが片方に残る** |
| ログ | 形式も保持期間も違い、**横断的な相関分析ができない** |
| ポリシー表現 | 同じルールを別記法で書き直し、**差異が入る** |
| 鍵管理 | 環境ごとに別サービス。**どこにどの鍵があるか把握できない** |
| 責任共有の境界 | サービスごとに違い、**「誰が見るべきか」の認識が抜ける** |

個々の環境が正しくても**全体の一貫性は保証されない**。インシデント時に「どこを見ればよいか」が分からないのが最大の運用リスク。責任共有モデルは [`../06_systems-security/05_distributed-systems-security.md`](../06_systems-security/05_distributed-systems-security.md)、第三国法の域外適用は [`../07_legal/03_regulatory-tsunami.md`](../07_legal/03_regulatory-tsunami.md)。

## 演習（解答つき）

1. 「認証」と「認可」の違いを一言で説明せよ。
2. BCP と DR の関係を、集合の言葉で説明せよ。
3. RTO=1 時間・RPO=1 時間のシステムと、RTO=24 時間・RPO=24 時間のシステムでは、一般にどちらの運用コストが高いか、理由とともに述べよ。
4. 3 つのクラウドを併用する組織が退職者のアクセス権を確実に剥奪するために、単一クラウドと比べて追加で必要になることを 2 つ挙げよ。

<details><summary>解答</summary>

1. 認証は「誰であるかの確認」、認可は「確認された相手に何を許すかの判断」。本人確認と権限判定は別の処理。
2. DR は BCP の**部分集合**。BCP は人員・拠点・プロセスを含む事業機能全体、DR はそのうち IT の技術的復旧。
3. RTO=1 時間・RPO=1 時間の方が高い。目標が短いほど常時稼働の冗長系・高頻度バックアップ・自動フェイルオーバー（自動切り替え）が必要で、コストは厳しさに比例して増える。
4. ①**3 環境それぞれで剥奪を確認する手順**（ID ストアが分断しているため）②**環境をまたいだ棚卸しの台帳**（誰がどこにアカウントを持つかの一元管理がないと漏れを検知できない）。ログ形式を正規化して「剥奪後のアクセスがない」ことを横断確認する仕組みも挙げられる。

</details>
